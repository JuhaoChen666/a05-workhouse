实验分析中遇到的问题与方案
在本次“校园二手物品交易平台系统规划与业务流程分析”实验中，小组主要遇到了以下问题，并采取了对应方案：
问题1：需求范围起初不清晰，功能边界容易扩大刚开始讨论时，大家把“社交、物流、支付、推荐”等都想一次性做完，导致系统目标不聚焦。方案： 先按课程要求确定核心范围，只保留“用户管理、商品管理、订单管理、评价与申诉管理”四条主线，把扩展功能（如智能推荐、校外物流）列为后续优化，不纳入本次主模型。
问题2：现状业务流程调查信息分散，流程难以标准化校园交易现状主要依赖微信群、校园墙和私聊，步骤不固定，很多情况靠口头协商，难以直接画标准流程图。方案： 采用“角色—事件—结果”方法先整理业务清单，再抽象为统一流程节点（发布、审核、下单、支付、交付、评价、申诉），最终形成现状流程图和优化流程图。
问题3：DFD分层时，功能与数据流容易混淆初版DFD里出现了“流程名像功能菜单、数据流名像动作描述”的问题，图不够规范。方案： 按DFD规范重新命名：处理过程用动词短语（如“订单管理”），数据流用名词（如“订单信息”“支付结果”），并补充数据存储（用户库、商品库、订单库、评价库），保证上下层一致。

校园二手物品交易平台系统规划与业务流程分析报告
1.系统规划与可行性分析
1.1项目背景
目前在高校中，学生之间的二手物品交易主要依赖以下几种方式：
①微信群/校园墙
通常是由学生自发建立的二手交易群，或者校园墙墙。其主要优点在于群成员众多，信息更新速度快，学生可以随时发布或浏览商品信息。交易灵活，几乎不产生平台费用，也不受时间和地点限制，只要打开群聊或朋友圈，便可以获取最新的交易信息，而且用户基本都是同一个学校或者附近区域的人，只要线下一手交钱一手交货就行，不会产生物流费用。缺点也很明显，商品信息杂乱无序，缺乏统一管理机制，商品发布质量参差不齐，图片不清晰、描述不完整或存在虚假信息的情况较多，交易安全性无法保障，容易出现欺诈或交易纠纷，此外，缺少高效的搜索和筛选功能，学生难以快速找到自己需要的目标商品。整体来看，这种方式效率低，信息利用率不高，且管理难度较大。
②商业二手平台
一般是成熟的二手交易平台，例如 闲鱼，转转，优点是支付和交易流程成熟，有保障措施，还有闲鱼小法庭等仲裁措施，使得维权更加方便，从而降低了交易风险，搜索商品方便，只要开启定位搜索可以很方便的找到附近的卖家。缺点是非校园专属，商品匹配效率低，对于校内学生的二手资源无法集中管理，学校里没人挂就买不到，平台可能收取手续费，校园内部资源无法充分利用，缺乏针对性服务。
而且这种二手平台上有大量虚假信息，闲鱼人称国内黑市，存在大量灰色地带商品，判断力较差的学生可能会受到不良影响，同时，二手平台上不止有学生群体，还有大量社会人士，用户可能会遇到例如“到手刀”，”仅退款“，”非平台交易诈骗“，“我是学生给我塞100”等各种套路，如果是经验不足的学生很容易中招，安全风险大。
根据以上信息，可以分析得到当前校园内二手交易市场存在以下几种问题：
(1)信息分散
商品信息分布在多个群，平台或者朋友圈贴文，缺乏集中管理。
学生难以快速获取所需商品信息，需要手动搜索或多渠道查找。
(2)交易不安全
买卖双方缺乏统一的身份验证和信用体系，容易发生虚假交易或欺诈行为。
缺乏在线支付监管机制，交易存在风险。
(3)效率低
商品发布、审核和上架流程繁琐，人工管理耗时长。
买卖双方沟通不畅，交易匹配速度慢。
无法快速统计校园内热门商品或交易趋势，信息滞后。
(4)缺乏统计与管理
交易数据无法集中记录和分析，学校管理部门难以了解二手物品流通情况。
缺少数据驱动的决策支持，如热门商品推荐或校园资源优化配置。
1.2 建设目标
1.2.1 系统建设目标
(1) 技术目标
建设一个基于Web和移动端的校园二手物品交易平台，实现商品发布、浏览、搜索、交易、支付和评价功能。平台应支持用户身份认证、商品信息统一管理和数据安全保障。系统应具备高并发处理能力，确保在校学生高峰使用时交易流畅，并实现数据可追溯、可统计。
(2) 管理目标
提供后台管理功能，支持管理员进行用户管理、商品审核、交易记录管理及报表统计分析。
实现自动化管理流程，减少人工干预，提高工作效率。
提供运营管理支持，包括活动推广、交易纠纷处理和数据分析，为学校和运营方提供决策依据。
(3) 经济目标
通过集中化、数字化的管理降低人工管理成本及交易风险，节约人力资源。
通过平台提供的广告位、服务费或增值服务实现经济收益，提升系统的经济价值。
预计建设成本在可控范围内，能够在短期内实现投资回报。
1.2.2系统建设必要性
(1)信息集中管理的需求：当前交易信息分散在微信群、论坛或商业平台，缺乏统一管理，导致学生难以高效获取交易信息，管理方难以监督。 
(2)交易安全和效率的需求：现有交易方式交易安全性低，沟通效率低，存在虚假信息和欺诈风险。建设专属平台可以通过用户认证、支付保障、评价机制和消息通知系统提升安全性和效率。 
(3)校园资源充分利用的需求：商业二手平台未能充分利用校园内部资源，如教材、寝室用品和课程相关物品，开发校园专属平台可实现资源优化配置。 
(4)数据统计与决策支持的需求：缺乏对二手物品流通情况的统计分析，无法为学校管理和运营提供数据支持。通过平台数据化管理，可以实现交易分析、热门商品推荐和运营决策优化。
1.3 系统可行性分析
1.3.1 技术可行性
技术方案：本系统采用前后端分离架构，前端使用Vue 3 + Element Plus开发，支持PC端和移动端；后端采用Node.js + Express框架，数据库采用MySQL存储用户、商品及订单信息；同时集成第三方支付接口,实现交易保障。 
开发难度：所选技术成熟、开发文档完善，社区支持良好，技术实现难度适中。系统功能模块化，易于开发和维护。 
可实现性：现有开发人员具备相关前后端开发经验，平台功能需求明确，系统可以在现有技术条件下顺利实现。

2 业务流程调查与优化
2.1 核心业务流程
(1)用户注册与登录
学生在平台上注册账户并登录，建立个人身份信息。
(2)商品发布
卖家填写商品信息（名称、价格、描述、图片），提交平台审核后上架。
(3)商品浏览与搜索
买家可以通过搜索、分类或推荐查看商品列表。
(4)下单与支付
买家选择商品下单，进行在线支付。
(5)订单管理与确认收货
平台记录订单状态，卖家发货后买家确认收货。
(6)评价与反馈
买家完成交易后对商品和卖家进行评价，形成信用记录

3.2 数据字典
3.2.1 数据流条目
（1）数据流名：用户注册信息
来源：学生用户
去向：1用户管理
说明：用户首次注册时提交的身份与账号信息
组成：学号 + 姓名 + 手机号 + 密码 + 验证码
(2）数据流名：商品发布信息
来源：学生用户（卖家）
去向：商品管理
说明：卖家发布商品时提交的信息
组成：商品标题 + 商品类别 + 成色 + 价格 + 描述 + 图片 + 联系方式
（3）数据流名：下单支付信息
来源：学生用户（买家）
去向：订单管理 / 第三方支付平台
说明：买家发起订单并完成支付时产生的信息
组成：订单编号 + 商品编号 + 买家编号 + 支付金额 + 支付方式 + 支付时间 + 支付状态
（4）数据流名：评价与反馈信息
来源：学生用户
去向：评价管理
说明：交易完成后提交的评价与举报内容
组成：订单编号 + 评分 + 评价内容 + 举报类型 + 证据附件 + 提交时间
3.2.2 数据存储条目
（1）数据存储名：用户信息库
输入数据流：用户注册信息、用户状态更新信息
输出数据流：用户身份信息、信用信息
说明：保存用户账号、认证状态、信用状态等基础资料
主要内容：用户标识 + 基本资料 + 认证状态 + 账号状态 + 信用记录
（2）数据存储名：商品信息库
输入数据流：商品发布信息、商品审核结果
输出数据流：商品列表信息、商品详情信息
说明：保存平台在售/下架商品信息
主要内容：商品标识 + 卖家标识 + 商品描述 + 价格信息 + 上下架状态
（3）数据存储名：订单信息库
输入数据流：下单支付信息、收货确认信息、退款处理信息
输出数据流：订单状态信息、交易统计信息
说明：保存订单生命周期全过程数据
主要内容：订单标识 + 买卖双方 + 金额信息 + 支付状态 + 交付状态 + 完成状态
（4）数据存储名：评价反馈库
输入数据流：评价与反馈信息、申诉处理结果
输出数据流：信用评价结果、违规处理记录
说明：保存评价、举报、仲裁等信息
主要内容：评价记录 + 举报记录 + 处理结果 + 信用变更记录

订单取消与退款规则
IF 订单状态 = 未支付 THEN
    买家可直接取消订单；
    系统将订单状态更新为“已取消”。
ELSE
    IF 订单状态 = 已支付 AND 交付状态 = 未交付 THEN
        买家可申请退款；
        系统发起原路退款；
        订单状态更新为“已退款”。
    ELSE
        IF 订单状态 = 已支付 AND 交付状态 = 已交付 AND 买家未确认收货 THEN
            买家可发起争议申请并上传证据；
            订单状态更新为“争议中”；
            管理员介入仲裁。
        ENDIF
    ENDIF
ENDIF
IF 管理员仲裁结果 = 买家责任 THEN
    平台驳回退款，订单状态更新为“已完成”。
ELSE IF 管理员仲裁结果 = 卖家责任 THEN
    平台执行退款，订单状态更新为“已退款”；
    卖家信用分扣减。
ENDIF
4 新系统逻辑模型
4.1 系统逻辑模型说明
基于现状流程优化和 DFD 分析，校园二手物品交易平台的新系统逻辑模型采用“前台业务 + 后台管理 + 规则引擎”三层逻辑结构。
系统围绕“用户—商品—订单—评价—申诉”主业务链运行，以实名认证、流程状态控制和信用机制保障交易安全，实现校园内二手资源高效流转与可治理管理。
4.2 新系统逻辑结构
表示层（用户交互层）
学生端：注册登录、商品发布、商品浏览、下单支付、评价反馈、申诉。
管理端：用户管理、商品审核、订单监控、申诉仲裁、统计报表。
业务逻辑层（核心处理层）
用户管理逻辑、商品管理逻辑、订单管理逻辑、评价信用逻辑、风控与申诉逻辑。
数据层（数据存储层）
用户库、商品库、订单库、评价库、申诉库、日志库。
4.3 主要功能模块划分
(1)用户管理模块
用户注册/登录、学号实名认证、账号状态管理、信用分维护。
(2)商品管理模块
商品发布、信息校验、审核上架、分类检索、下架管理。
(3)订单管理模块
下单、支付、交付、确认收货、取消退款、状态跟踪。
(4)评价管理模块
双方互评、评价展示、信用累计、恶意评价识别。
(5)申诉与风控模块
举报受理、证据提交、管理员仲裁、违规处罚。
(6)后台统计与运营模块
成交统计、热门品类分析、用户活跃分析、风险预警。
4.5 新系统相对旧系统的改进点
和以前在微信群、校园墙里交易相比，新系统最大的变化是把原来零散、靠私聊推进的过程，变成了一个统一的平台流程。
以前找商品要翻很多聊天记录，现在可以直接按分类和关键词搜索，效率高很多。交易方式上，以前基本靠双方口头约定，出了问题也很难说清。现在从下单、支付、交付到确认收货、评价都有记录，交易过程更清楚，也更方便后续查询。在可信度方面，旧方式几乎没有身份约束，容易出现虚假信息。
新系统加入了实名认证和信用分机制，用户行为会沉淀为信用记录，对不诚信行为有一定约束作用。
管理方式也有明显提升。过去主要靠管理员人工盯群、凭经验处理问题；现在平台能自动汇总交易数据和异常情况，管理人员可以根据数据做判断，处理更及时，也更有依据。
另外，纠纷处理从“出了事再私下协商”变成“有规则可走”。通过审核、风控和申诉仲裁机制，很多风险可以提前拦截，真发生争议也有标准流程处理，整体安全性更高。

# Resume library API and thumbnails

`GET /api/resume-library?page=1&page_size=24` requires the existing Bearer token. It returns `items`, `total`, `page`, `page_size`, `uploaded_total`, and `generated_total`. Each item has a stable `key` (`uploaded:<integer>` or `generated:<UUID>`), `kind`, `id`, `name`, `format`, `updated_at`, and nullable `thumbnail_url`. Generated items also expose their existing document summary fields and a `document` summary. The old upload, list, delete, rename, copy, preview, and download routes remain available.

The list derives identity from `trusted_owner`; it does not accept a query `user_id`. It reads legacy uploads through their existing session and saved documents through the resume-storage session, counts each complete source, then merges only the requested page prefix from each source. Page numbers are limited to 1–10,000 and page sizes to 1–100. Ordering is descending update time, then a stable kind and typed ID tie-break. Naive legacy upload times use `RESUME_LEGACY_TIMEZONE` when configured, otherwise the service process's local timezone; naive generated-document times are UTC. Responses use ISO timestamps with an explicit UTC offset. If historical uploads were written in a timezone different from the current server timezone, configure the original zone explicitly; history is not rewritten.

The nullable thumbnail URL is a protected API path such as `/api/resume-library/thumbnail/generated/<UUID>`. Clients must request it with the Bearer header and display the returned PNG Blob; tokens do not belong in URLs. The read route checks the trusted owner, the source owner, and the source's current deletion state. Old documents and render failures return `null` and continue to use the frontend placeholder.

Successful PDF uploads and generated documents register a durable row in `resume_thumbnails`. The existing `app.services.resume_worker` gives at most one thumbnail a chance on each worker cycle, even when it also processes a compilation job. It uses a database lock to keep thumbnail rendering to one task per configured database. PDFium runs in a spawned child process with an 8-second timeout; the renderer accepts sources up to 20 MiB and emits a PNG up to 2 MiB, at most 1,000,000 pixels and 1,200 pixels on either edge. A task has at most three attempts. Failed thumbnail work does not roll back the saved PDF/document.

The worker requires `RESUME_PRIVATE_ASSET_ROOT` to point at the already configured dedicated private-asset directory. Upload thumbnails are read only from the established `LEGACY_ROOTS`; paths outside those roots, links, missing records, and changed source hashes fail closed. Generated copies may share the same PNG. Existing generated-document retention cleanup releases each expired copy's reference and removes shared bytes only after no other thumbnail record protects them. A hard-deleted legacy upload currently makes its thumbnail URL return 404; its derived asset is retained pending a separately controlled cleanup path.

`requirements-phase2.txt` includes the renderer and timezone data needed by this path. Apply the additive Alembic revision `resume_thumbnail_001` before enabling thumbnail registration in a deployed database. The migration was not applied as part of this change. Its downgrade drops the table only after an online check confirms it is empty; records or assets cause downgrade to stop. No worker, maintenance cleanup, history backfill, or production migration was run.
